# Research: GitHub CLI (`gh`) Extension Configuration and Persistent Storage

## 1. Official/Best Practice for Storing Configuration and Data
The GitHub CLI (`gh`) ecosystem treats extensions as standalone executables (e.g., `gh-my-ext`) that act independently of the core `gh` application's internals. 

**Best Practice:** Extensions should create their own dedicated directories under standard OS-specific base directories, using the extension's name (e.g., `gh-copilot`) rather than nesting inside `gh`'s own configuration folders.

**Sources & Evidence:**
- **Popular Extensions in the Wild:**
  - Official GitHub extensions like [`gh-copilot`](https://github.com/github/gh-copilot) store configuration in `~/.config/gh-copilot/` (as discussed in `cli/cli` [issue #8857](https://github.com/cli/cli/issues/8857)).
  - Third-party extensions like [`gh-codeowners`](https://github.com/heaths/gh-codeowners) and [`gh-dash`](https://github.com/dlvhdr/gh-dash) use `~/.config/gh-codeowners/` and `~/.config/gh-dash/`, respectively.
- **The `go-gh` Library Warning:** The official `github.com/cli/go-gh/v2/pkg/config` module (the Go library designed for authoring GitHub CLI extensions) explicitly warns against using the `gh` internal configuration API for extensions:
  > `"// Note: This package is intended for use only in gh, any other use cases are subject to breakage and non-backwards compatible updates."` ([Source: `go-gh` config.go](https://github.com/cli/go-gh/blob/trunk/pkg/config/config.go))

## 2. Is it acceptable to add a custom folder to `~/.config/gh/`?
**It is not recommended.** You should avoid writing extension persistent data or configuration into `~/.config/gh/` (or `$XDG_CONFIG_HOME/gh/`) for the following reasons:

- **Namespace Ownership:** The `gh` subdirectory is owned by the core GitHub CLI. Adding custom directories (e.g., `~/.config/gh/gh-install/`) risks naming collisions with future features of the `gh` tool.
- **Uninstall Behavior:** `gh extension remove <ext>` only removes the extension's binary and manifest from the `gh` data directory (where it was installed). It **does not** clean up configuration or state files generated by the extension (confirmed as expected behavior in `cli/cli` [issue #8857](https://github.com/cli/cli/issues/8857)). Littering the core `gh` folder with orphaned configuration files is bad practice.
- **Lack of Support:** There are no APIs provided by the `gh` CLI to inject or manage extension configurations natively inside the `gh` config folder.

## 3. Where exactly should persistent data be stored by a `gh` extension?
Extensions should adhere to the **XDG Base Directory Specification** on Linux/macOS, and use equivalent native paths on Windows. Assuming your extension is named `gh-install`, the data should be stored as follows:

| Data Type | Environment Variable | Default Path (Unix/Linux/macOS) | Windows Fallback |
| :--- | :--- | :--- | :--- |
| **Configuration** (e.g., `config.yml`, JSON config) | `$XDG_CONFIG_HOME` | `~/.config/gh-install/` | `%AppData%\gh-install\` |
| **Data** (e.g., persistent databases, downloaded assets) | `$XDG_DATA_HOME` | `~/.local/share/gh-install/` | `%AppData%\gh-install\` |
| **State** (e.g., logs, history) | `$XDG_STATE_HOME` | `~/.local/state/gh-install/` | `%AppData%\gh-install\` |
| **Cache** | `$XDG_CACHE_HOME` | `~/.cache/gh-install/` | `%LocalAppData%\gh-install\` |

**Note on Windows:** If you choose to adopt the same path-resolution logic that the `gh` CLI ecosystem natively uses, the `go-gh` library looks for `LocalAppData` or `AppData` environment variables for Windows users.

**Implementation Recommendation:** 
If you are authoring the extension in Go, consider using a standard path-resolution library like [`adrg/xdg`](https://github.com/adrg/xdg) or standard library functions (`os.UserConfigDir()`) and suffixing it with your extension's name:
```go
configDir, _ := os.UserConfigDir()
extensionConfigPath := filepath.Join(configDir, "gh-install", "config.json")
```
